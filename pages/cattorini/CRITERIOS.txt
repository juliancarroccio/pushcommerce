────────────────────────────
LANDING
────────────────────────────

1
dado un cliente
cuando entra a la landing page
entonces visualiza la página con un hero
y la historia
y un catálogo con las tres líneas de producción
y una selección de destacados dinámica
y un link para que se de de alta como mayorista
y un link para que el mayorista registrado consulte el estado de su solicitud mayorista
y una sección con el local actual
y una parte con el contacto con mapa del lugar con días, horarios y mapa disponible

2
dado un cliente
cuando hace click en solicitar cuenta mayorista
entonces se abre un formulario con datos para completar (validar que se pidan los que están ahora en los tests)

3
dado un cliente
cuando hace click en solicitar cuenta mayorista
y completa el formulario con datos relevantes (validar que se pida dirección y datos en tests)
y presiona enviar solicitud
entonces se crea una solicitud de mayorista
y recibe un código de seguimiento de dicha solicitud
y el local desde portal puede aceptar o rechazar

3.1
dado un cliente
cuando llega a la landing con hash "#mayoristas" desde otra página
entonces la página scrollea automáticamente a la sección Mayoristas
y el botón "Solicitar cuenta mayorista" se resalta con animación pulse por 3 iteraciones

3.2
dado un cliente
cuando envía el formulario de solicitud mayorista sin completar nombre o negocio
entonces se muestra el mensaje "Nombre y negocio son obligatorios"
y el pedido NO se crea

3.3
dado un cliente
cuando envía el formulario sin WhatsApp ni email
entonces se muestra el mensaje "Necesitamos WhatsApp o email para contactarte"

3.4
dado un cliente
cuando envía el formulario sin provincia o sin localidad
entonces se muestra el mensaje "Elegí provincia y localidad"

3.5
dado un cliente
cuando ingresa una localidad que no existe en la lista de la provincia elegida
entonces se muestra el mensaje "Elegí una localidad de la lista sugerida"

3.6
dado un cliente
cuando envía el formulario sin dirección
entonces se muestra el mensaje "Ingresá la dirección para poder enviarte pedidos por Vía Cargo"

3.7
dado un cliente
cuando envía la solicitud correctamente
entonces se muestra un modal de confirmación con código MAY-XXXX
y se ofrece un link "Ver estado de mi solicitud"
y el código se guarda en localStorage bajo "catt_mis_solicitudes" para acceso rápido futuro

3.7.1
dado un cliente
cuando en el formulario de solicitud adjunta una foto del negocio (campo opcional, input file)
entonces la imagen se redimensiona a máximo 640px de lado más largo y se comprime a JPEG calidad 60% en el navegador
y se envía como string base64 en solicitante.foto_negocio dentro del mismo documento de Firestore
(no requiere Firebase Storage — el sitio no tiene ese servicio activado)
y las Firestore rules rechazan el string si supera 700.000 caracteres

3.7.2
dado un cliente
cuando envía la solicitud SIN adjuntar foto
entonces solicitante.foto_negocio se guarda como null
y la solicitud se procesa igual, sin ningún campo obligatorio de por medio

3.7.3
dado un cliente
cuando cierra el modal y lo vuelve a abrir para una segunda solicitud
entonces el campo de foto y su preview se resetean
(no arrastra la foto de una solicitud anterior a la siguiente)

3.8
dado un cliente
cuando reintenta enviar dos solicitudes seguidas dentro de 5 segundos
entonces la segunda es rechazada por rate limit
y se muestra "Esperá unos segundos antes de reintentar"

3.9
dado un cliente
cuando scrollea por las secciones de la landing
entonces cada sección aparece con animación (fade + slide up)
y las 5 fotos de Historia rotan como carrusel automático cada 5.5s en el hero
y las 3 fotos de la sección "Nuestra Producción" (antes "Fábrica") rotan cada 4.5s con dots
y las 3 fotos de Local rotan en la sección respectiva cada 4.5s con dots

3.9.1
dado un visitante
cuando ve el hero y la sección "Nuestra Producción"
entonces el texto indica que Cattorini es una marca textil de Las Flores desde 1959
y ningún texto afirma fabricación propia, máquinas propias ni "cada prenda pasa por nuestras manos"
(la producción está tercerizada; los textos no lo mencionan explícitamente pero tampoco afirman lo contrario)

3.10
dado un cliente
cuando scrollea más de 800px desde el inicio
entonces aparece un botón flotante de WhatsApp en la esquina inferior derecha

13.1

cuando entra a la tienda

dado un cliente

dado un cliente ya identificado

13.5
dado un cliente minorista de zona libre con bonificación configurada
cuando entra a la tienda
entonces visualiza el badge "Cliente minorista · Localidad · Para tu zona tenemos X% de descuento"
y los precios muestran el precio original tachado + precio con descuento
y cada card tiene un badge "-X%"

13.6
dado un cliente
cuando se identifica correctamente
y luego cierra el navegador
y vuelve a abrir la tienda en el mismo dispositivo
entonces mantiene su perfil (localStorage persiste)
y para mayoristas se re-valida el hash contra la config actual

13.6.1
dado un cliente mayorista con código individual (con dirección guardada)
cuando se identifica correctamente
y cierra el navegador por completo (no solo la pestaña)
y vuelve a entrar más tarde en una sesión nueva
entonces "catt_codigo_valido_hash" persiste en localStorage (no en sessionStorage)
y el perfil mayorista sigue válido
y el checkout sigue autocompletando nombre, negocio y dirección con los datos guardados
(bug corregido: antes ese hash vivía en sessionStorage mientras el resto del perfil vivía en
localStorage, así que al cerrar el navegador se perdía la validación y el checkout dejaba de
autocompletar aunque el código siguiera siendo válido — el comportamiento era intermitente
según si era la misma pestaña/sesión o una nueva)

13.7
dado un cliente mayorista con código individual
cuando el admin elimina su registro de mayoristas_activos
y el cliente vuelve a entrar en una nueva sesión
entonces al validar el perfil persistido, su código deja de funcionar
y se le fuerza a re-identificarse

────────────────────────────

15.7
dado un producto con fabricacion_propia = false
cuando un cliente mayorista ve el catálogo
entonces el producto NO aparece en el listado
(el catálogo mayorista es solo de fabricación propia)

15.8

(compatibilidad hacia atrás: no desaparece nada del catálogo mayorista existente)

TIENDA — PRODUCTO DETALLE
────────────────────────────

16
dado cliente mayorista/minorista
cuando entra a la tienda
y hace click a algún producto
entonces visualiza el producto más detallado
y puede ver una o más fotos del producto
y la guía de talle asignada al producto
y puede elegir talle, color (si el producto tiene stock/color cargado en el portal) y cantidad
y puede agregar el producto con el talle, color y cantidad al carrito

16.1
dado un cliente
cuando entra a /producto.html?id=X con un ID inexistente
o un producto con disponible=false
entonces se muestra la pantalla "Producto no encontrado"
y un link para volver al catálogo

16.2
dado un cliente
cuando entra al detalle de un producto
y NO ha elegido talle
entonces el botón "Agregar al carrito" está deshabilitado

16.3
dado un cliente
cuando hace click en un talle marcado como no disponible
entonces el botón no responde (disabled)
y visualmente el talle se ve tachado y opaco

16.4
dado un cliente
cuando hace click en "Ver guía de talles"
entonces se abre un modal con la tabla de medidas del tipo de prenda
y las columnas se corresponden con las medidas definidas en productos.json
y las filas muestran cada talle y sus valores

16.5
dado un cliente en el detalle de producto con múltiples imágenes
cuando hace click en un thumbnail
entonces la imagen principal cambia
y el thumbnail activo tiene borde negro destacado

16.6
dado un cliente
cuando agrega un producto al carrito
entonces se muestra un toast "Agregado · Talle X ×Y"
y el badge del carrito aumenta la cantidad

16.7
dado un cliente
cuando agrega el mismo producto con el mismo talle 2 veces
entonces el carrito consolida a un solo item con qty sumada
en vez de duplicar la línea

16.8
dado un cliente mayorista con código individual
cuando entra al detalle de un producto
entonces ve el precio mayorista con el tag "Precio mayorista"
y el JSON-LD Product en la página tiene ese precio para SEO

16.9
dado un cliente
cuando cambia la cantidad con +/-
entonces la cantidad se limita entre 1 y 999


────────────────────────────
TIENDA — STOCK Y COLOR POR TALLE
────────────────────────────

16.10
dado un producto con stock cargado en Firestore (colección stock/{productId})
cuando un cliente elige un talle en la ficha del producto
entonces se muestran los colores disponibles para ESE talle específico
como chips con un círculo del color + el nombre (ej: círculo rojo + "Rojo")

16.11
dado un color de un talle con cantidad > 3
cuando el cliente lo selecciona
entonces se muestra "X disponibles" debajo del selector

16.12
dado un color de un talle con cantidad entre 1 y 3
cuando el cliente lo selecciona
entonces se muestra "¡Últimas X unidades!" para generar urgencia

16.13
dado un color de un talle con cantidad = 0
cuando el cliente ve el selector de colores
entonces ese color aparece tachado/deshabilitado y no se puede elegir

16.14
dado un producto SIN ningún color cargado en Stock para el talle elegido (o sin doc de stock en absoluto)
cuando el cliente elige el talle
entonces no se muestra selector de color
y el botón "Agregar al carrito" se habilita solo con el talle, igual que antes de esta funcionalidad
(compatibilidad hacia atrás: productos sin stock cargado no se rompen)

16.15
dado un cliente que agregó al carrito un producto con color elegido
cuando llega al checkout y confirma el pedido
entonces se ejecuta una transacción atómica contra Firestore que verifica el stock de ese talle+color
y si no alcanza, el pedido NO se crea y se le muestra un mensaje indicando cuánto queda disponible
y si alcanza, se descuenta la cantidad del pedido del stock y se registra un movimiento en el historial con motivo "Venta #CÓDIGO"

16.16
dado dos clientes que intentan comprar la última unidad de un talle+color al mismo tiempo
cuando ambos confirman casi simultáneamente
entonces la transacción atómica garantiza que solo uno de los dos consiga la unidad
y el otro recibe el mensaje de stock insuficiente

TIENDA — CHECKOUT MAYORISTA
────────────────────────────

30
dado un cliente mayorista con datos en mayoristas_activos
cuando abre el carrito
entonces visualiza el panel resumen con nombre, negocio, WhatsApp, email y dirección
y NO visualiza el input de nombre

31
dado un cliente mayorista con datos y dirección registrada
cuando elige "Envío a domicilio"
entonces los campos de dirección aparecen pre-llenados y deshabilitados (fondo gris)
y aparece el header "Enviamos a tu dirección registrada" con botón "Editar"

32
dado un cliente mayorista con dirección pre-llenada
cuando hace click en "Editar"
entonces los campos se desbloquean
y el header desaparece
y el foco va al input de dirección

33
dado un cliente mayorista con datos
cuando confirma pedido con envío
y no editó la dirección
entonces se guarda el pedido con los datos originales del mayorista

34
dado un cliente mayorista con datos
cuando confirma pedido con envío
y editó la dirección para enviar a otro lado
entonces se guarda el pedido con la nueva dirección
pero manteniendo nombre, negocio y datos personales del mayorista

35
dado un cliente mayorista SIN dirección registrada
cuando elige envío
entonces los campos aparecen vacíos y editables directo
sin el header de "Editar"

36
dado un cliente mayorista
cuando confirma pedido
entonces el payload en Firebase incluye: negocio, whatsapp, email, cuit del mayorista
para que el admin identifique el pedido en el panel

36.1
dado un cliente mayorista
cuando elige envío y el subtotal supera config.envio.gratis_desde
entonces el envío NO se bonifica — siempre se cobra config.envio.costo_estandar
(el envío gratis por monto es un beneficio exclusivo de minoristas; el envío mayorista
siempre corre por cuenta del comprador, sin excepción)

36.2
dado un cliente mayorista
cuando ve el banner informativo de envío (en tienda.html y en producto.html)
entonces el texto es "Envíos por {transportista}. El costo de envío se discrimina
aparte y se suma al total en el carrito." (NO menciona "envío gratis", que es
exclusivo de minoristas)
y el mismo banner se actualiza en vivo si el cliente cambia de perfil sin recargar la página

36.3
dado un cliente mayorista
cuando el subtotal del carrito es menor a config.mayoristas.minimo_compra
entonces se muestra un cartel de advertencia con el monto que falta para llegar al mínimo
y el botón "Confirmar pedido" queda deshabilitado
(aplica tanto en tienda.html como en producto.html — ver criterio 60.x para la
defensa equivalente del lado servidor/sendOrder)

36.4
dado un cliente mayorista
cuando el subtotal alcanza o supera config.mayoristas.minimo_compra
entonces el cartel de advertencia desaparece
y el botón "Confirmar pedido" se habilita

36.5
dado un cliente minorista
cuando revisa el carrito, sin importar el subtotal
entonces nunca ve el cartel de mínimo de compra (esa validación es exclusiva de mayoristas)

36.6
dado un cliente mayorista bajo el mínimo de compra
cuando fuerza el envío del pedido saltándose la UI (ej. dispara sendOrder() manualmente)
entonces la función igual bloquea la creación del pedido y no se guarda nada en Firestore
(la validación del mínimo no es solo cosmética/UI — está duplicada como defensa real)

TIENDA — VALIDACIONES ANTI-FRAUDE
────────────────────────────

37
dado un cliente minorista
cuando en el gate ingresó una localidad libre
y en el checkout elige envío a una localidad con distribuidor registrado
entonces al confirmar el pedido se muestra el modal "No podemos enviarte a esa localidad"
con datos del distribuidor
y el pedido NO se envía

38
dado un cliente mayorista
cuando en el checkout elige envío a una localidad con distribuidor registrado (para minoristas)
entonces el pedido se envía normalmente
(los mayoristas no tienen restricción de zona)

39
dado un cliente
cuando envía dos pedidos dentro de 2.5 segundos
entonces la segunda confirmación es rechazada por rate limit
y se muestra "Esperá unos segundos antes de reenviar"

40
dado un bot
cuando completa el formulario incluyendo el campo honeypot #hp-website
entonces el pedido no se procesa (validación anti-spam)

41
dado un cliente
cuando Firebase no está disponible (o db es null)
entonces se muestra "Sistema de pedidos no disponible. Recargá la página."
y el pedido no queda como "confirmado" falsamente

42
dado un cliente
cuando confirma pedido correctamente
entonces se muestra modal con código de seguimiento tipo #ABCDE
y el código + docId se guarda en localStorage bajo "catt_mis_pedidos"

y si el pedido requiere pago electrónico (ver sección siguiente), se muestra además el QR de pago


────────────────────────────
TIENDA — PAGO EN RETIRO Y FLUJO QR
────────────────────────────

Regla general: un pedido "necesita QR" si es de modalidad envío (siempre),
o si es de modalidad retiro y el cliente eligió "Pago electrónico (QR)" en vez de
"Pago en el local". Cuando un pedido necesita QR, el comportamiento es IDÉNTICO
sea envío o retiro — mismo QR, mismo mensaje, mismo estado.

42.1
dado un cliente que elige "Retiro en local"
cuando abre el selector "¿Cómo vas a pagar?"
entonces ve dos opciones: "Pago en el local" (activa por default) y "Pago electrónico (QR)"
y un texto de ayuda que cambia según la opción elegida

42.2
dado un cliente que elige "Envío a domicilio"
cuando mira el carrito
entonces el selector "¿Cómo vas a pagar?" no se muestra (el envío siempre es pago electrónico)

42.3
dado un cliente que confirma un pedido que necesita QR (envío, o retiro + pago electrónico)
cuando ve la pantalla de confirmación
entonces además del código de seguimiento se muestra:
- el texto "Pedido pendiente de pago"
- un QR (imagen configurada por Cattorini en el portal, tab "Datos de pago")
- el titular y el banco de la cuenta destino (config.pago.titular / config.pago.banco),
  como segundo chequeo por si el QR falla el escaneo o el cliente prefiere transferir a mano
- instrucciones de escanear con cualquier billetera virtual que ofrezca pagos QR
- un link de WhatsApp por si prefiere pagar por otro medio
y el pedido queda guardado en Firestore con estado "pendiente" y pagaEnLocal=false

42.3.1
dado un cliente con un pedido pendiente de pago (QR)
cuando vuelve más tarde a /seguimiento.html?code=XXX sin haber pagado todavía
entonces se le vuelve a mostrar el mismo bloque de QR + titular + banco
(no solo aparece una vez en la confirmación inicial — el cliente puede necesitar
volver a consultarlo)

42.4
dado un cliente que confirma un pedido de retiro con "Pago en el local"
cuando ve la pantalla de confirmación
entonces NO se muestra el QR
y el mensaje dice que el pedido queda a la espera de que Cattorini lo confirme,
y que lo va a abonar cuando pase a retirarlo
y el pedido queda guardado en Firestore con estado "pendiente" y pagaEnLocal=true

42.5
dado el payload de un pedido guardado en Firestore
cuando se inspecciona el campo pagaEnLocal
entonces es true solo si modalidad=retiro Y el cliente eligió pago en el local
y es false en cualquier otro caso (envío siempre, o retiro con pago QR)

42.6
dado el admin
cuando carga un pedido manual de modalidad retiro desde pedidos.html (+ Manual)
entonces el pedido se guarda con pagaEnLocal=true automáticamente
(se asume que el pago ya se arregló en persona/teléfono; los pedidos manuales no
disparan el flujo QR)

SEGURIDAD Y EDGE CASES

133
dado un atacante
cuando hace fetch a /pages/cattorini/portal.html en Google
entonces la página tiene meta robots="noindex,nofollow" y no aparece en resultados
y en robots.txt está Disallow: /portal.html

134
dado un atacante
cuando intenta escribir en Firestore fuera del shape esperado
entonces las security rules rechazan el request
y el pedido no se crea

135
dado un atacante
cuando intenta hacer un update/delete en pedidos sin autenticar
entonces las security rules deniegan (require request.auth != null)

136
dado un atacante
cuando descarga productos.json
entonces solo obtiene el HASH del código master (no el código plaintext)
y no puede recuperar el código por brute-force razonable

137
dado un atacante
cuando trata de listar mayoristas_activos
entonces las rules deniegan (list solo con auth)
pero puede hacer get puntual si conoce el hash exacto de un código
(la seguridad viene del espacio 2^256 de SHA-256)

138
dado un cliente
cuando el navegador o red bloquea Firestore
entonces la tienda sigue funcionando en modo lectura (catálogo, precios)
pero al confirmar pedido se muestra un error explícito, no un falso éxito

139
dado un cliente
cuando la app se sirve desde bfcache (botón "atrás" de Chrome)
entonces al restaurar la página se remueve la clase "leaving" del body
y la página vuelve a ser visible inmediatamente

140
dado un cliente
cuando el Service Worker v2 detecta una versión nueva del sitio
entonces la activa automáticamente (skipWaiting + clients.claim)
y las próximas requests HTML/JS son network-first (siempre traen lo último)


────────────────────────────
NOTAS PARA TESTING
────────────────────────────

- El campo "código de seguimiento" es alfanumérico [A-Z2-9] de 5 caracteres (pedidos) o "MAY-" + 4 caracteres (solicitudes) o "CATT-" + 6 caracteres (códigos mayorista)
- El hash SHA-256 se calcula en cliente con crypto.subtle.digest
- Firebase Auth es anónima (no requiere email/pass del cliente)
- Los datos sensibles (PAT, contraseña) nunca se guardan en Firestore
- localStorage keys usadas:
  * catt_perfil, catt_localidad, catt_zona_status
  * catt_mayorista_data
  * catt_codigo_valido_hash (movido de sessionStorage a localStorage — ver criterio 13.6.1)
  * catt_cart_v2
  * catt_mis_pedidos, catt_mis_solicitudes
  * catt_epat, catt_epat_meta (portal)
- sessionStorage keys:
  * catt_pat_session, catt_pedidos_session
- Firestore: el stock (colección `stock/{productId}` + subcolección `movimientos`) es la
  única parte del catálogo que NO vive en productos.json — ver sección "PORTAL — TAB STOCK"
  y FIRESTORE-RULES.md
- Nota sobre el bug de "publish no sube cambios" (reportado por el cliente, no confirmado
  al 100% con lectura estática de código): se aplicaron mitigaciones defensivas en
  publishChanges() (re-fetch del SHA remoto antes de publicar, comparación de contenido
  real antes/después con aviso explícito si no hay cambios) pero no se pudo aislar una
  causa raíz verificable — pendiente de reproducir en producción
